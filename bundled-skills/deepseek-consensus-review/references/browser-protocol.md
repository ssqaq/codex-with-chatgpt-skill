# 浏览器恢复、快速读取和完整复测（1.19.1）

## 当前浏览器入口

1. 优先使用宿主实际提供的 `mcp__cua_repl.js`。首次调用严格按工具文档初始化；当前入口是 `cua.getState()`，随后用实际浏览器和标签 ID 选择原标签。仅旧宿主确实提供并有文档的 `mcp__node_repl.js` 才使用旧接口。
2. 不导入内部浏览器包，不枚举对象原型猜 API，不寻找旧全局变量。页面操作、读取、恢复均通过宿主公开工具，不另建 HTTP、CDP、Playwright 连接或浏览器状态机。
3. 当前工具的成功浏览器清单加原标签 DOM，是可核对的页面证据。映射旧回执字段时，清单可填 `OpenTabsEvidence=confirmed`；另一来源不存在时保留 `TabsListEvidence=unknown`。不能伪造一次 `user.openTabs()` 或 `tabs.list()` 调用。仍须满足原页面消息 present、至少一个标签来源 confirmed、没有 wrong-session。
4. 使用 DeepSeek 页面实际模型，确认深度思考和智能搜索开启，不再寻找已取消的“专家模式”按钮。模型说明填“网页当前模型（合并升级版）”，不能由提示词声称切换模型。

## 恢复原对话

1. 先读当前 Task 的绑定和 nextAction。临时 `frozen + auto-recover-runtime-tab` 是仅恢复状态，不是任务完成；停止、取消、失败终态不可借此恢复执行权限。
2. 工具暂时断开时保留原官方会话、原消息指纹和回执。重新获取内置浏览器后核对原 URL 与 session，不依据当前焦点或同名标签猜测。
3. 成功清单确认原标签已关闭且无同会话重复标签时，可打开保存的原官方对话 URL，再执行 `RecoverRuntimeTab`。这是重新打开原对话，不是新建官方会话；有 pendingReceipt 时先找回页面核对发送落点，不重发。
4. 每个任务可以恢复多次；同一次故障自动恢复最多一次，60 秒内核对同一 session、当前 tab、runtime、新 epoch 和页面开关；失败保留现场并回显具体原因，不持续试接口或重连。恢复不会重置本轮计时，也不会清除未知回执。
5. 用户已授权“原对话确实找不回时新建”的任务：优先恢复原地址；确认原对话不存在、当前工具可用且没有重复官方会话后，允许新建并携带已确认的需求、轮次、方案和分歧摘要。没有这个授权时不擅自替换。工具断开、加载超时、需要登录或发送落点未知仍暂停，不能当成原对话丢失。
6. 当前工具的丢失证据使用 `LossEvidenceSources=cua.getState,original-url`：成功清单证明没有可复用官方会话，访问原地址后页面明确提示原对话不存在，至少两次实际观察。调用 MarkLost 时填 OriginalConversationStatus=not-found、BrowserToolStatus=available、原 DomTargetUrl、OpenTabsEvidence=absent，旧来源 TabsListEvidence 保留 unknown。脚本本身不访问网页，所有证据必须实际读取。随后按现有 BeginBootstrap -ReplaceLost 建立新绑定，保持一个专用官方会话和标签，不另造状态机。
7. 未确认发送先核对原消息，present 只补回执，unknown 停止重发并说明卡点；允许新建不等于允许重复发送。新对话只携带已确认的摘要与真实当前轮次，不伪称它拥有原网页历史或已完成新的共识。
8. 恢复次数按评审 Task 计算。前任务正常结束后新 Task Claim 复用会话会清零并保留旧恢复审计；同一 Task 的重复 Claim 不能清零。旧版已经 Claim 的休眠记录只有前任务终态、尚无当前浏览器/发送动作和待回执风险时才迁移，未知情况保留原记录。

## 连续完成一轮

1. 摘要准备完成后才取得 lease、读取新鲜页面并准备发送。使用现有用户授权，不重复询问已授权范围；如宿主实际提出审批，遵循真实审批结果，不伪造 token。
2. `send_review_round.ps1` 返回 ready 后立即由浏览器填写、提交和核对落点。脚本自身没有发送能力。已发送/未知落点时不重发。
3. 发送回执确认后立即读取当前回复；两次实际检查间隔不超过 30 秒。每次仅提取当前轮助手回复、生成状态和必要身份；执行端按 `review get --json` 的 polling 调度，有实际延迟就记录，不用密集空转命令补次数。
4. 观察后调用 `review observe`。`progressFingerprint` 只取当前助手回复内容，不使用用户消息、思考区、动画或网页时钟。回复结束立即读取完整结果，不能等到下一分钟再处理。
5. 调用 `review reply --evidence <文件>` 校验本轮回复。证据包含 taskId、threadId、round、source=codex-in-app-browser、observationId、observedAt、conversationUrl、role=assistant、complete=true、messageFingerprint、replyFingerprint 和 text。text 是实际助手短评审正文（最多 2400 字），必须有唯一且匹配的 TASK_ID、ROUND、DECISION；replyFingerprint 为该正文的 SHA256。
6. `reply` 只验证浏览器证据，不代替 Codex 核对。随后连续调用原 `review_round.ps1 -Action RecordRound`、状态更新及 `review sync`；有修改意见才 `review prepare` 进入下一轮。重复记录同一回复不能再次推进或执行。
7. 双方同意且范围、文件方向、测试和成功标准齐全，才确认共识并调用 `review execute`，由 Codex 真正修改和测试。记录 handoff 请求不代表新任务已经创建；没有真实接手结果不能宣称已执行。不得把本机状态命令当作改变宿主计划模式的能力。

## 正文结束判断与小范围读取

1. 先用本轮实际已发消息定位用户消息容器，再读紧接着的助手正文。思考区、侧栏历史摘要、用户消息中的 CONSENSUS 均不能作为回复。页面当前结构可用 `.ds-message` 和 `.ds-assistant-message-main-content` 区分消息与正文；使用前核对实际 DOM，不把这些类名当永久 API。
2. 完成判断优先依据本轮助手正文后的完整操作栏（复制、重新生成等）与生成按钮恢复，而不是“文字暂时没变化”。短回复可能没有“本回答由 AI 生成”那行提示，不能等待这行文字。思考区出现“已思考”也不代表正文已经结束。
3. 2026-09-12 实测的操作栏位于助手 `.ds-message` 后的 `.ds-flex` 元素，有至少三个按钮；正文旁已经确认出现该操作栏时可以结束等待。页面结构变了或仍有停止生成控件时保持未完成，做一次结构核对，不在后台重新连接。
4. 直接绑定经过核验的已有官方会话时用 `BindExistingOfficialSession`；空白页首次建立才用 `BeginBootstrap`。没有观察到 marker 就保持空，不把预期 marker 写成已观察证据。`BrowserRuntimeId` 是执行端为本次控制连接保存的本地标识，重建时更换并递增 RuntimeEpoch，不假装是官网返回的 ID。
5. 后续轮次只评变更和必要结论，默认回复上限 600 字；需要更短时使用摘要中的上限。不要为了固定轮数反复索要已同意内容，也不要将专项验收描述成未解决分歧。

## 时间和完成证据

1. `review get --json` 输出 polling 和 timing。timing 保存各轮消息就绪、提交、首次回复观察、完整回复观察、Codex 核对、共识和恢复时间，以及实际执行起止；旧记录缺少时返回 null，不补造。
2. 网页等待是“提交到观察到完整回复”，包含观察间隔和期间恢复；与恢复时长不能重复相加。网页显示的思考时间只作附注。每满一分钟回显原轮次和最近真实检查时间；Codex 不运行时不能承诺定时更新。
3. 纯“收到”往返只算连通测试。完整复测需要真实方案意见、3–4 轮专项检查、双方共识、实际文件修改、测试回执、页面检查和修改后独立复核；若提前一致，后续明确做边界专项复核，不伪造分歧。
4. 独立测试项目和证据目录不能包含凭据或完整业务代码。发布报告分开列自动化模拟、真实网页和实际执行结果，失败时继续修复，不能写全部通过。

## 复测发现的衔接问题

1. 先把本轮完整消息放入当前浏览器调用的变量，再取得页面证据和发送许可。不要在30秒发送窗口内重新拼长消息或做无关修改。
2. 页面提交后先回读本轮用户消息并立即记 confirmed 回执、释放 lease，之后再等助手回复。不要持有发送锁等待模型生成；过期时在核对原页后重新 AcquireBrowserLease，仅补录旧消息回执，禁止重新 PrepareSend 或重新提交。
3. 每次读取明确传入当前 message、TASK_ID 和 ROUND。持久 REPL 里的旧函数可能保留上一轮变量，不能直接复用捕获旧消息的闭包。参考 [read-current-reply.js](read-current-reply.js)，按工具文档将函数声明放入 REPL，每次传参，不导入内部浏览器模块。
4. 完整操作栏只证明这一条回复结束，仍须核对当前任务和轮次。读到旧轮次时不记录内容进展、不推进；立即核对定位函数和原消息一次，再按30秒以内的检查间隔读取。不能原样重复调用错误定位等十分钟。
5. 本地脚本任何一步失败，后续记录、复制文件和测试不得继续串行执行；PowerShell 调用外部命令后检查 LASTEXITCODE 或使用会抛错的包装器。
6. sendPageVerifiedAt 只保存本轮发送前页面证据时间，后续回执和恢复不覆盖。同一时间的UTC和带时区字符串按时间点比较；PowerShell读取ISO日期后仍保留毫秒，旧数据缺字段不补造。
7. 实际修改与本机检查通过后调用 review final-prepare，保存 executionVerifiedAt，单独发结果摘要。最终复核已通过才能 finish；原执行起点不重置，不重复写业务文件。最终复核轮数不计入方案轮数。
8. 发送前把本轮消息与读取函数准备好，再取新鲜页面证据；发送窗口内不拼消息、不解释方案。30秒以内的检查目标需由当前宿主实际调度，跨工具处理超时如实记录；不能仅靠写入规则声称变快。页面导航后若选择器超时，先重新读取页面状态确认加载结果，不盲目重复点击或重复发送。

## 1.19.2：检查间隔上限30秒

1. 发送后立即读取一次。后续30秒是从上一次实际 observedAt 算起的上限，回执、状态保存、恢复与工具调度都占用这段时间；不能处理完再额外等30秒。可以提前检查，读到完整回复就立即核对。
2. review get 的 checkAfterMs 是距下次检查截止还剩多少毫秒，已到期时为0。执行端应提前发起浏览器读取，超出上限记录真实延迟，不能用取整或改写历史时间掩盖。
3. 每满一分钟回显及连续10分钟无内容进展暂停保持原规则。旧复测记录中的5/15秒目标和当时延迟保留为历史，不按新口径倒改。

## 1.19.3：及时保存回复，减少跨工具等待

1. 已确认发送并释放锁后，可使用读取示例里的 pollCurrentReply，在一次 CUA 调用中约每5秒检查一次，最多调度20秒。读到完整本轮回复立即返回，不主动等满20秒；每次仍显式传入本轮消息、任务号和轮次。
2. 20秒包含读取耗时，到截止后不发起下一次读取；已经发出的工具调用受宿主超时控制，可能超过20秒，必须保留实际耗时并计入30秒检查目标，不宣称可以取消底层调用。不要在持有发送锁时批量等待。
3. 返回 observations 和 error。先按真实 observedAt 顺序保存所有成功观察，再做详细分析。失败调用不生成成功观察；后续失败也不抹掉之前成功的记录。错轮立即返回错误，错轮文字不能更新检查时间或内容进展。出现 error 时暂停或按原规则恢复，不重发、不推进、不取得共识。
4. 完整回复先调用 review observe / review reply 保存并校验，随后再核对建议、记录轮次和准备下一步。超过60秒的证据必须真实重新读取，不改历史时间。页面观察本身不等于双方同意；核心共识、取消和执行门槛保留。
5. 返回仍未完成时，扣除状态保存、回显和工具调度耗时，按 polling.checkAfterMs 在30秒截止前再次读取；每满一分钟仍回显。第一轮也遵循摘要里更短的回复要求，避免简单专项产生过长回复。
6. 计划提前通过但用户指定的专项还未完成时，记录本轮同意、剩余专项和待敲定状态，不提前确认整体执行共识，也不编造分歧。全部专项完成后才双方确认并执行。

## 同一个任务多次恢复

1. 任务恢复成功后又发生新的真实故障，可以再次恢复，累计次数另行记录。同一次故障失败后不循环重连；取消、终态、未知发送和十分钟无内容进展保护保留。新任务不继承旧故障次数。
2. 原标签已经关闭但工具和原对话可用时，调用 RecoverRuntimeTab 并传入 ClosedTabEvidenceFile。此分支不消耗工具故障的恢复次数；要求原回执 confirmed、无 pendingReceipt/auditRisk、原身份匹配、无租约且 epoch 递增。
3. 证据是60秒内成功 cua.getState 返回的当前内置浏览器标签清单，加原对话实际 DOM 核验。JSON 字段为 source=cua.getState、taskId、threadId、browserSurface=codex-in-app-sidebar、capturedAt、oldTabId、tabs=[{id,url}]。只保存当前内置浏览器必要字段。旧标签必须已不在清单，新标签必须是原地址的唯一匹配。不得用空白清单、加载慢或外部浏览器代替。
4. 重开后的标签又被关闭时，可用新的真实清单恢复；旧清单因 oldTabId 不匹配而拒绝。保留原回执、任务、轮次和计时，不新建官方对话、不重发、不直接取得执行权限。
